### Beachhead — ใคร และหาเจอที่ไหน

**ติวเตอร์เดี่ยว 11–30 คน ยังไม่มีแอดมิน สอนเด็กที่มีผู้ปกครองจ่าย** — กลุ่มนี้เจอโอนช้า 76% ใช้เวลาสิ้นเดือน >3 ชม. 41% รับราคา 299 ที่ 71% (สูงสุดทุกกลุ่ม)

ไม่เอา: 1–10 คน (43% บอกไม่สนใจ · pain ยังไม่พอ) · 31+ คน (หลายรายจ้างแอดมินคนจริงแล้ว)

**ผู้สมัครวง 1 มีชื่อแล้วจากสัมภาษณ์:** มายด์ (13 คน เกลียดจัดตาราง ยอมจ่าย 200–300) · กวิสรา (10 คน อยาก "ระบบตามยอดคล้ายขุนทอง") — ไม่ต้องหาใหม่ โทรหาสองคนนี้

**ช่องทางหลังวง 1:** กลุ่ม Facebook ติวเตอร์ · LINE OpenChat ติวเตอร์ · เครือข่ายนิสิตสอนพิเศษใน มก. ที่ทีมเข้าถึงได้เอง — ทั้งหมดฟรี และเป็นที่ที่ครูบอกต่อกันเอง

### คู่แข่ง และเหตุผลที่เราต่าง

| ทางเลือกที่ครูใช้อยู่ | จุดอ่อน | เราต่างตรงไหน |
|---|---|---|

| ขุนทอง (ถูกพูดถึง 2 ครั้ง) | ทวงในนามบอท ไม่รู้จักคาบเรียน | เสียงครู · รู้ว่าเรียนไปกี่ครั้ง |
| แพลตฟอร์มติว (หักค่าหัว) | ยึดผู้ปกครองไปเป็นของแพลตฟอร์ม | **เราไม่ถือเงิน ไม่ยึดลูกค้า** — นี่คือ wedge |

### โมเดลรายได้

299/เดือน คิดเฉพาะเดือนที่ส่งบิล · ฟรี ≤5 คน · ต้นทุนเซิร์ฟเวอร์ ≈ 0 บนฟรีเทียร์จนถึงราว 100 ผู้ใช้
**เป้า 90 วัน: 10 ครูจ่ายจริง = 2,990/เดือน** ไม่ใช่เงิน แต่คือหลักฐานที่ TAM บนสไลด์ให้ไม่ได้

### วิสัยทัศน์ vs โฟกัส

โค้ด `core/` `app/` ไม่รู้จักอาชีพ — คงไว้ เพราะราคาถูกและพิสูจน์แล้วว่าเพิ่มอาชีพแตะไฟล์เดียว
แต่**แรงของทีมทั้งหมดลงที่ติวเตอร์** จนกว่าจะมีคนจ่าย 299 คนแรก — บรรทัด "เร็ว ๆ นี้" บนหน้าแรกพอแล้วสำหรับสัญญาณ

## 2 · CTO — สถาปัตยกรรมที่จะพาไปถึงตรงนั้น

### สิ่งที่ถูกแล้ว ห้ามแตะ

- `core/` เป็น pure function · ตัวเลขทุกตัว derive จาก ledger · ไม่มี state ซ้ำซ้อน
- profession isolation ที่พิสูจน์แล้วด้วยการเพิ่มอาชีพทดสอบ
- วินัยเทส: ทุก assertion ใหม่ต้องพิสูจน์ว่าฟ้องแดงก่อนนับ — จับบั๊กเงินได้จริงมาแล้ว

### เพดานของ static + localStorage

| ทำไม่ได้เลย | เสี่ยง |
|---|---|
| ลิงก์ผู้ปกครอง (ข้อมูลอยู่เครื่องครู) | Safari ล้าง storage เว็บที่ไม่เปิด 7 วัน — ปิดเทอม = หาย |
| ครูเปิดจากมือถือและคอมแล้วเห็นชุดเดียวกัน | ล้างแคช = หาย |
| เตือนอะไรตอนไม่ได้เปิดแอป | เลขที่ใบเสร็จชนกันถ้ามีสองเครื่อง |

### การตัดสินใจ: Supabase — และทำไมไม่ใช่อย่างอื่น

| ตัวเลือก | ปฏิเสธเพราะ |
|---|---|
| Firebase | NoSQL ไม่เหมาะกับ ledger ที่ต้อง join · RLS อ่อนกว่า |
| Cloudflare D1 + Workers | ต้องเขียน auth และ API เองทั้งหมด |
| PocketBase | ต้องมีเครื่องรัน — ทีมนิสิตไม่ควรดูแลเซิร์ฟเวอร์ |
| **Supabase** | Postgres + auth + RLS + ฟรีเทียร์ · ตาราง 1:1 กับ `AppState` วันนี้ · ลิงก์ผู้ปกครองทำได้ด้วย policy เดียว |

### 3 จุดที่แก้วันนี้ ไม่งั้น migrate เจ็บทีหลัง

| แก้ | ทำไมต้องตอนนี้ | แรง |
|---|---|---|
| id → `crypto.randomUUID()` | id แบบ counter ชนกันทันทีที่มีสองเครื่อง · เปลี่ยนตอนมีข้อมูลจริงแล้ว = ต้อง remap ทุก foreign key | 1 ชม. |
| `providerId` ทุก entity ระดับบน | RLS ต้องใช้ · เติมทีหลังต้องเดาว่าแถวไหนของใคร | 30 นาที |
| `updatedAt` ทุก entity ที่แก้ได้ | conflict resolution ตอน sync · ไม่มี = เขียนทับกันเงียบ ๆ | 30 นาที |

### โมเดลบน Postgres (วง 2)

ตาราง 1:1 กับ array ใน `AppState`: `clients · subjects · units · completions · invoices · payments · receipts · messages · notes · events` + `providers` + `counters`
- **RLS:** ทุกตารางอ่าน/เขียนได้เฉพาะ `provider_id = auth.uid()`
- **ลิงก์ผู้ปกครอง:** view `public_invoice` ที่ SELECT ได้ด้วย id เท่านั้น (uuid เดาไม่ได้) ไม่มี listing ไม่ต้อง login
- **เลขที่ใบเสร็จ:** `UPDATE counters … RETURNING` — atomic ที่ DB ไม่ใช่ที่ client
- **Auth ครู:** magic link ทางอีเมลก่อน (ง่ายสุด) · LINE Login เป็น phase ถัดไปเพราะ UX ดีกว่าสำหรับคนไทยแต่เพิ่ม OAuth
- **Offline-first:** reducer ยังเป็นทางเขียนเดียว · localStorage เป็น cache · effect หลัง action diff แล้ว upsert แถวที่ `updatedAt` เปลี่ยน · ออฟไลน์ = คิวไว้ — ครูสอนในที่สัญญาณไม่ดีต้องยังแตะได้

### ความปลอดภัย

- token ของ LINE OA ห้ามอยู่ใน frontend ตลอดกาล — นี่คือเหตุผลเดียวก็พอที่ OA ต้องรอ backend
- ลิงก์ผู้ปกครองเป็น read-only เห็นแค่ใบเดียว ไม่เห็นรายชื่อคนอื่น
- ไฟล์สำรอง JSON มีชื่อเด็กและผู้ปกครอง — บอกครูให้เก็บเหมือนสมุดบัญชี

### LINE — ตอนนี้ และทีหลัง

**ตอนนี้ (ทำแล้ว):** share link · ข้อความออกจากบัญชีครู · ครูกดส่งเอง · ไม่มีอะไรต้องแอด
**หลังมีรายได้:** OA ของ Solo หรือ OA ของครูเอง — เมื่อมี server, มีคนจ่าย, และมีเหตุผลให้ผู้ปกครองแอดเพิ่ม (เช่น ดูตารางเอง)

## 6 · ความเสี่ยง และแผนรับมือ

| ความเสี่ยง | โอกาส | รับมือ |
|---|---|---|
| ครูวง 1 ไม่แตะเช็คชื่อเลย | สูง — เป็นข้อเสี่ยงสุด | นั่งดู onboarding · ถ้าไม่แตะใน 3 วัน โทรถามทันที ไม่รอครบสัปดาห์ |
| ข้อมูลครูหายระหว่างวง 1 | กลาง | PWA + สำรองทุก 3 วัน + บอกล่วงหน้าตรง ๆ |
| Safari บล็อก `window.open` ไป LINE | กลาง | fallback คัดลอกทำแล้ว · ทดสอบบน iPhone จริงก่อนส่งให้ครู |
| ทีมอยากเพิ่มฟีเจอร์ระหว่างวง 1 | สูง | กติกาสัปดาห์ 2: แก้บั๊กเท่านั้น |
| migrate localStorage → Supabase ทำข้อมูลครูเพี้ยน | กลาง | เทสด้วยไฟล์สำรองจริงของครู ไม่ใช่ fixture · เก็บไฟล์เดิมไว้จนยืนยัน |
| วันแข่งมาก่อนสัปดาห์ 3 | ไม่รู้ | **ต้องรู้วันแข่ง** — ถ้าแข่งก่อน ให้จบวง 1 แล้วเล่าผลวง 1 นั่นแหละคือหลักฐานที่กรรมการอยากเห็น |

## 7 · ต้องการจากคุณ

1. **วันแข่ง** — กำหนดว่าสัปดาห์ 3–4 อยู่ก่อนหรือหลังเวที
2. **ติดต่อมายด์กับกวิสราได้ไหม** — ถ้าได้ บอกวิธีเก็บเงินของเขา (รายครั้ง/เดือน/แพ็ก) ผมจะ seed onboarding ให้ตรงเคส
3. **ใครในทีมเป็นคนคุยกับครูวง 1** — ต้องเป็นคนเดียวที่โทรทุก 3 วัน ไม่ใช่ทั้งทีม
4. **ยืนยันตัด `/pitch`** — จะทำในสัปดาห์ 1

ถ้าตอบข้อ 1 กับ 4 ผมเริ่ม `refactor(ids)` ได้ทันที — ข้อ 2–3 ไม่บล็อกโค้ด
